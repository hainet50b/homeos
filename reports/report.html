Add --print flag to cd-family commands

Judgement points

  • Threaded print as an explicit bool parameter through cd::run, package::cd, and plugin::cd rather than introducing a new RunMode enum or a separate print_path entry point. The flag is binary at the call site and the function bodies are short, so a parameter is the least invasive shape.

Could be worth a clarifying note.

cd-family Windows shell fallback (pwsh → powershell)

Judgement points

The task asked for a single source of truth for Windows shell selection reachable from both the cd-family subshell path (src/commands.rs) and the action-execution path (src/commands/package/mod.rs). I lifted pwsh_on_path() / pwsh_on_path_in() into the parent commands module and added a shared windows_shell_for(pwsh_available) helper that owns the pwsh-vs-powershell decision. The action path's shell_command_for stayed in package/mod.rs because its Unix arm returns sh (not the subshell's /bin/sh); only its Windows arm now delegates to the shared helper. I kept the two contexts' Unix defaults distinct rather than forcing them to share, since they were already intentionally different.

To make the new fallback testable without depending on the host's PATH or compile-time cfg!(windows), I introduced resolve_shell_with(shell_env, is_windows, pwsh_available) — mirroring the existing shell_command_for parameter-injection pattern — and had the production resolve_shell delegate to it. The old host-dependent test_resolve_shell_falls_back_when_env_unset (which asserted pwsh on Windows and would now be wrong/flaky on a pwsh-less Windows host) was replaced with four deterministic parametrized cases (env-var-wins, Unix, Windows+pwsh, Windows-no-pwsh).

Unresolved / workarounds

The development host (Windows) has no MSVC toolchain, Windows SDK, or Visual Studio installed, so link.exe is absent and MSVC-target builds cannot link locally. Per the project's documented convention (Windows is verified via the Build CI workflow on push; local verification is on Linux), I ran cargo fmt --check, cargo clippy -- -D warnings, and cargo test inside WSL Fedora after installing the toolchain there (gcc rust cargo rustfmt clippy git). All 819 tests pass on Linux. The #[cfg(windows)]-gated tests in package/mod.rs are not exercised on Linux; they are unchanged in behavior and will run on the Windows CI job. A git identity had to be set in WSL for the clone-based test helpers to commit their fixture repos.

Next PRD suggestions

The test fixture helpers (create_local_git_repo in git.rs, init.rs, and plugin/registry.rs) call git commit without passing -c user.name / -c user.email and ignore the commit's exit status. On any machine without a global git identity, the fixture commits silently fail and the clone-based tests produce confusing "Not a valid homeos plugin/repo" failures rather than a clear setup error. Consider a follow-up task to pin a deterministic identity in those helpers (e.g. git -c user.name=homeos-test -c user.email=test@homeos.local commit ...) so the suite is self-contained regardless of ambient git config.

Change summary

On a fresh Windows machine with only Windows PowerShell 5.1, homeos cd, homeos package cd, and homeos plugin cd no longer fail with "program not found" — they now fall back to powershell when pwsh (PowerShell 7+) is not on PATH, matching the fallback already used for action-script execution. Statically link the MSVC C runtime into Windows binaries

Judgement points

  • Added a new .cargo/config.toml at the repository root with a single [target.'cfg(target_env = "msvc")'] section setting rustflags = ["-C", "target-feature=+crt-static"], exactly as the task and the Windows binary linkage note in SPEC/SPEC.md prescribe. Using the cfg(target_env = "msvc") predicate (rather than naming the two MSVC targets explicitly) is the idiomatic way to cover both x86_64-pc-windows-msvc and aarch64-pc-windows-msvc at once while leaving Linux/macOS untouched, and it also applies to local Windows dev builds for dev/release parity.
  • Added a short comment block at the top of the config explaining the why (vcruntime140.dll on a fresh machine) so the next reader doesn't have to reconstruct the rationale from git history.
  • No .rs source, README.md, or COMMAND_OUTPUT.md changes — the task scopes this to a build-config addition with no user-visible output change, and the spec note in SPEC/SPEC.md was already present.

Unresolved / workarounds

  • Local compile/link checks could not be run on this host. The development machine has no MSVC toolchain installed — no Visual Studio / Build Tools, no cl.exe / external link.exe, and no Windows SDK (kernel32.lib is absent). The x86_64-pc-windows-msvc target requires both an MSVC linker and the SDK import libraries, so cargo clippy / cargo test fail at the link stage regardless of this change — the same limitation prior Windows-specific entries in this report noted. What was verified locally: cargo fmt --check passes, and cargo build -v confirms every MSVC-target rustc invocation now carries -C target-feature=+crt-static, i.e. the config is valid TOML and is correctly picked up and applied by cargo. Full compile/link/test verification rests on the CI Build workflow across all targets, which the task explicitly designates as sufficient for this Windows-only concern.

Next PRD suggestions

That would turn the "no Redistributable needed" guarantee into an enforced invariant rather than a build-config assumption.

Change summary

Released homeos.exe for Windows now statically links the MSVC C runtime, so the binary starts on a clean Windows install without first installing the Visual C++ Redistributable (vcruntime140.dll) — removing a fresh-machine bootstrap failure. Linux and macOS builds are unaffected.

Enforce Windows CRT independence in CI

  • In release.yml the step sits between Build and Package (Windows) so the exact artifact about to be zipped is what gets verified. It inspects target/${{ matrix.target }}/release/homeos.exe, which works unchanged for both the x86_64 entry and the cross-built aarch64 entry — dumpbin /dependents parses a PE regardless of its target architecture.

The (?i) gives the required case-insensitivity; the api-ms-win-crt- arm is included because +crt-static statically links the UCRT too, so its forwarder DLLs must also be absent.

De-flake the Windows suite: drop the PATH-mutating shell_command tests

Judgement points

The two #[cfg(windows)] tests in src/commands/package/mod.rs (test_shell_command_falls_back_when_pwsh_absent_on_windows and test_shell_command_prefers_pwsh_when_present_on_windows) faked pwsh presence/absence by rewriting the process-global PATH via EnvVarGuard. Rust runs the whole binary's tests on parallel threads in one process, so during that mutation window any concurrently-spawning test resolved binaries against the clobbered PATH — observed as plugin refresh tests panicking at Command::new("git") with program not found, a different failing set every run.

I chose to delete both rather than rewrite them. The decision logic they covered is already fully exercised without touching global state: shell_command_for(is_windows, pwsh_available) (same module) and pwsh_on_path_in(&path) (in crate::commands) are both parameter-injected. The only thing the deleted pair added was the one-line composition shell_command() = shell_command_for(cfg!(windows), pwsh_on_path()), which the PRD task explicitly says is acceptable to drop. I left a comment in their place documenting why no test wires that composition together, so a future contributor doesn't "helpfully" re-add the racy version.

Unresolved / workarounds

None. Audited the whole suite for other EnvVarGuard::capture("PATH") usage — these two were the only ones, as the PRD predicted. EnvVarGuard itself stays; it's used for lower-risk vars (HOMEOS_DATA_DIR, HOMEOS_OUTPUT_FORMAT, etc.) that no concurrent test reads implicitly during a subprocess spawn.

OS-appropriate action-script fixtures for a stock Windows machine

Judgement points

The ~40 action-script fixtures in src/commands/package/action.rs wrote POSIX sh bodies (#!/usr/bin/env sh + touch '<marker>') into the OS-named script file — which on Windows is *.ps1, run under PowerShell. touch resolves there only when GNU coreutils happen to be on PATH (true on GitHub runners and some dev installs, false on a stock Windows + default Git install), so 25+ tests failed with The term 'touch' is not recognized.

Introduced one helper next to the fixtures, marker_script(marker: &Path) -> String, returning New-Item -ItemType File -Path '…' | Out-Null on Windows and the existing sh/touch body elsewhere, and routed every executed fixture through it (the two shared helpers fixture_with_script/write_script, all inline fixtures, and the two tests that previously inlined their own cfg!(windows) branch). Three judgement calls:

  • Unmodified-skeleton fixtures (the Generated by homeos ones with a live touch side-effect): routed through the helper with the marker comment prepended. These are classified as skipped and never execute, but making the side-effect OS-appropriate keeps the negative assertion (!marker.exists()) meaningful on Windows — a broken skip would actually create the marker and be caught.
  • The two skeleton literals with no touch (content-is-the-subject, never executed) were left as literal strings, as the task permits.
  • The exit 1 failure scripts were left untouched: under PowerShell the #!/usr/bin/env sh line is just a comment and exit 1 runs natively, so they were never part of the failing set. Kept scope to the touch problem.

The loop-binding case (marker: &PathBuf) uses marker_script(marker) without an extra borrow to avoid a clippy needless_borrow; owned-PathBuf sites use marker_script(&marker). No production code changed.

None.

Execute Windows action scripts with -NoProfile -File

Judgement points

The task suggested a helper signature of script_invocation(shell, script), but a test on a Linux/macOS host cannot assert the Windows form unless the OS is injectable. I added an is_windows: bool first parameter, matching the existing shell_command_for(is_windows, pwsh_available) convention already in mod.rs — single source of truth for "am I on Windows" in the helper layer. execute_script calls it with cfg!(windows).

The helper returns (&str, Vec<&OsStr>) (borrowed, no allocation): the flag literals are 'static and the script's OsStr borrows the caller's Path. This keeps the script path as an OsStr rather than a lossy String, so paths with non-UTF-8 / unusual characters pass through to the shell intact.

Unresolved / workarounds

None.

Next PRD suggestions

With this landed, all Windows-bootstrap and Windows-hardening tasks in the current ledger are complete. No new tasks surfaced. The only follow-up I'd flag is purely observational: the SPEC already documents the -NoProfile -File behaviour (maintainer-owned), so no spec drift to reconcile.

Change summary

On Windows, action scripts (install/update/uninstall via install, update, uninstall, apply) now run as <shell> -NoProfile -File <script> instead of bare <shell> <script>. Scripts no longer load the user's $PROFILE (no hidden machine-local aliases/functions, no profile startup cost, no profile output mixed into script output), and the explicit -File fixes a latent powershell.exe fallback bug where a bare path was treated as -Command. Unix sh <script> is unchanged.
