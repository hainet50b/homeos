Add --print flag to cd-family commands

Judgement points

  • Threaded print as an explicit bool parameter through cd::run, package::cd, and plugin::cd rather than introducing a new RunMode enum or a separate print_path entry point. The flag is binary at the call site and the function bodies are short, so a parameter is the least invasive shape.
  • Reused the existing ctx.output_format() for text vs JSON dispatch instead of plumbing a separate format argument — keeps --print aligned with the existing --json contract.
  • Skipped both the update_check::check_and_notify call and agents_md::refresh_if_stale when --print is set on homeos cd, matching the spec's "no side effects" requirement. Verified via a unit test that writes a stale AGENTS.md and asserts it is left untouched.
  • For the homeos cd --print error case, the existing resolve_target error path is reused — it already returns data-dir-not-found per the spec, so no additional error wiring was needed.

Unresolved / workarounds

  • None.

Next PRD suggestions

  • Consider a follow-up to add --print-aware completion hints (e.g., shell aliases like hcd that wrap cd "$(homeos cd --print)") — the spec mentions the use case but doesn't ship sugar for it.
  • The data-dir-not-found error path for homeos cd --print is symmetric with the default mode, but homeos package cd --print / homeos plugin cd --print do not error if the optional subdirectory exists but the parent homeos.yml is missing — they bubble the load error, which is fine but not explicitly enumerated in the spec. Could be worth a clarifying note.

Change summary

homeos cd, homeos package cd, and homeos plugin cd now accept a --print flag that prints the absolute target path to stdout and exits without launching a shell. JSON mode emits {"path": "..."}. homeos cd --print skips the AGENTS.md refresh and update-check side effects.

Review highlights

  • Side-effect suppression for homeos cd --print is covered by test_run_print_emits_data_dir_to_writer_without_side_effects in src/commands/cd.rs — it stales AGENTS.md and asserts it is not regenerated by the print path. Worth a glance to confirm the test exercises the right invariant.
  • The unit tests for print formatting are pure (no filesystem) and assert exact strings, which makes them brittle if the JSON shape ever changes. That feels right given the spec ties the JSON envelope to a single fixed key.

Add Plugin column to homeos package list

Judgement points

  • Column placement followed the spec exactly: Package, Enabled, Installed, Plugin, Dependencies. The Plugin separator is sized to the widest value (consistent with the existing Package and Dependencies columns), matching the README sample where the separator under Plugin is six dashes (header width) because no value exceeds it.
  • For the JSON field I placed plugin between installed and depends_on to mirror the schema block in COMMAND_OUTPUT.md. Since PackageConfig.plugin is already Option<String>, serde_json::json! renders it as a string or null with no extra handling.
  • Text-mode uses "-" for the absent case via unwrap_or_else; JSON keeps null rather than "-" so consumers can distinguish "no plugin" structurally.
